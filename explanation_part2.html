1. What is Exploratory Data Analysis (EDA)?

Before building any machine learning model, you need to understand your data deeply. This is what EDA does. It's the process of investigating your dataset to discover patterns, spot anomalies, test hypotheses, and check assumptions — all using statistical summaries and visual techniques.

Analogy: EDA is like walking through a house before buying it. You check every room, look for cracks in the walls, test the plumbing, and measure the rooms. You wouldn't buy a house blind — and you shouldn't build a model without understanding your data first.

Why Do We Do EDA?

  • Understand data quality: Are there missing values? Duplicates? Wrong data types?
  • Discover patterns: Which features matter? How do they relate to the target?
  • Spot anomalies: Are there outliers that need handling?
  • Guide feature engineering: What new features could we create based on what we learn?
  • Inform model selection: Is the data linear? Do we need tree-based models?
  • Handle class imbalance: Is the target variable balanced? (Spoiler: ours isn't)

2. Data Quality Checks

Before diving into analysis, we must verify the data is clean. Think of this as a health check-up for your dataset. Three critical checks: missing values, duplicates, and data types.

2.1 Missing Values Check

Why it matters: Machine learning models can't handle missing values. If we have gaps, we'd need to impute (fill in) or drop rows. Both strategies have consequences — imputation introduces assumptions, and dropping rows loses information. Knowing the extent of the problem tells us how to handle it. 

# Check for missing values

Result: Zero missing values across all 25 columns! This is a clean dataset. In real-world projects, you'd typically see 5-30% missing values in some columns. Our UCI dataset was carefully curated for research, so it came pre-cleaned.

2.2 Duplicate Rows Check

Why it matters: Duplicate rows can bias the model. If the same customer record appears twice, the model might "over-learn" that pattern, essentially giving that record double the importance it should have. This leads to overfitting on duplicated records. 

# Check for duplicate rows

# Check for duplicate IDs

Result: No duplicate rows and no duplicate customer IDs. Each of the 30,000 records is unique. This confirms data integrity — no accidental double-entry.

Understanding Class Imbalance

The ratio of non-defaulters to defaulters is 3.5 : 1. For every person who defaults, roughly 3.5 people pay on time. This is called class imbalance.

Analogy — Why Accuracy is Misleading:
Imagine an exam where 22 out of 100 students fail. A "teacher" who guesses "Everyone passes!" without looking at any work would be right 78% of the time. That's 78% accuracy with zero intelligence.

This is exactly the trap with imbalanced data. A model that always predicts "No Default" would achieve 78% accuracy but would be completely useless — it would never catch a single defaulter!

Why We Use ROC-AUC Instead of Accuracy

Accuracy (Misleading)

  • Dumb model: always predict "No Default" = 78% accuracy
  • Looks good on paper, fails in practice
  • Doesn't tell you about the model's ability to find defaulters
  • Deceived by class imbalance

ROC-AUC (Reliable)

  • Measures ability to distinguish classes at ALL thresholds
  • AUC of 0.5 = random guessing, 1.0 = perfect
  • Works regardless of class ratio
  • Our model achieves 0.814 — genuinely good
Analogy for ROC-AUC: Imagine sorting a deck of cards into red and black while blindfolded. AUC = 0.5 is randomly guessing (like flipping a coin). AUC = 1.0 is perfect sorting. Our model's 0.814 means it sorts cards correctly about 81% of the time — not perfect, but far better than random. In the credit card world, that's excellent.

8. Outlier Detection

Outliers are data points that are significantly different from the rest. Think of them as "unusual suspects" in your data — someone with a 800,000 NT$ credit limit when most have 50,000-240,000.

8.1 The IQR Method

We use the Interquartile Range (IQR) method to detect outliers. Here's how it works:

IQR Method Visualized

The method splits data into quartiles and flags anything beyond 1.5x the IQR range as an outlier:

# Outlier detection using IQR method
for feature in outlier_features:
    Q1 = df[feature].quantile(0.25)
    Q3 = df[feature].quantile(0.75)
    IQR = Q3 - Q1
    lower_bound = Q1 - 1.5 * IQR
    upper_bound = Q3 + 1.5 * IQR

    outliers = df[(df[feature] < lower_bound) | (df[feature] > upper_bound)]
    outlier_count = len(outliers)
    outlier_percentage = (outlier_count / len(df)) * 100

    print(f"{feature}:")
    print(f"  Lower bound: {lower_bound:.2f}")
    print(f"  Upper bound: {upper_bound:.2f}")
    print(f"  Outliers: {outlier_count:,} ({outlier_percentage:.1f}%)")

8.3 Why We Kept the Outliers

Critical Decision: We did NOT remove or cap the outliers. Here's why:

Why We Kept Them

  • Tree-based models (XGBoost, CatBoost) are naturally robust to outliers
  • They split on thresholds, so extreme values are simply placed in the right branch
  • Outliers represent real customers with genuinely high bills or payments
  • Removing them would lose information about extreme-risk profiles
  • The outliers might be exactly the defaulters we want to predict!

When We Would Remove Them

  • If using distance-based models (KNN, SVM) that are sensitive to outliers
  • If outliers were data entry errors (not real values)
  • If using linear regression (heavily affected by extreme points)
  • If the outlier percentage was much higher (>15-20%)
