1. Problem Statement

A bank wants to predict whether a credit card customer will default on their payment next month. They have historical data on 30,000 customers including their demographics, payment history over 6 months, bill amounts, and payment amounts. Our job is to build a machine learning model that learns patterns from this history and predicts whether a given customer will default (1) or not (0).

In simple terms: Given a customer's credit limit, age, gender, education, marriage status, and 6 months of payment/bill data — will they fail to pay their credit card bill next month?

Why This Problem Matters

Credit card default is one of the biggest risks for banks. If a customer defaults, the bank loses money. By predicting defaults before they happen, banks can:

  • Send early warning alerts to at-risk customers
  • Adjust credit limits proactively
  • Reduce bad debt and financial losses
  • Offer restructuring options before it's too late

2.2 Dataset Size Justification

Why 30,000 Rows Is Good

  • Statistically significant for model training
  • Allows 80/20 split: 24,000 train / 6,000 test
  • Enough samples for both classes (~6,636 defaults)
  • Fast training time with tree-based models
  • Large enough to detect subtle patterns

Potential Limitations

  • Only Taiwanese customers (may not generalize globally)
  • Data from 2005 (consumer behavior may have changed)
  • Relatively small for deep learning approaches
  • Limited to tabular data (no unstructured data)
Key Decision: We chose this dataset because it's clean, well-documented, has a realistic class imbalance (~22% default rate), and is widely used as a benchmark in academic research. The 30,000 rows are sufficient for traditional ML models (tree-based, linear) which are ideal for tabular data of this size.

3. Target Variable Analysis

The target variable default.payment.next.month tells us whether the customer defaulted:

No Default (0): 23,364 customers (77.9%)
Default (1): 6,636 customers (22.1%)
Class Imbalance Ratio: ~3.5:1
For every 1 defaulter, there are ~3.5 non-defaulters
Why This Matters: The dataset is imbalanced (78% vs 22%). This means:
  • A model that always predicts "No Default" would be 78% accurate but useless
  • We need metrics beyond accuracy — that's why we use ROC-AUC
  • ROC-AUC measures the model's ability to distinguish between classes regardless of balance

7. Key Design Decisions & Justifications

Decision 1: 80/20 Train-Test Split

We split the data 80% train (24,000 rows) and 20% test (6,000 rows) with random_state=42 for reproducibility.

Why 80/20? This is the industry standard split. It gives the model enough data to learn (80%) while reserving a substantial test set (20% = 6,000 samples) to reliably evaluate performance. With 6,000 test samples, even small differences in performance are statistically meaningful.

Decision 2: ROC-AUC as Primary Metric

We used ROC-AUC instead of accuracy because of class imbalance (78% vs 22%).

Why ROC-AUC? Accuracy is misleading with imbalanced data. A dumb model predicting "No Default" for everyone gets 78% accuracy. ROC-AUC measures how well the model separates the two classes across ALL possible thresholds, giving a much better picture of true model quality.

Decision 3: No SMOTE / Oversampling

We explicitly chose NOT to use SMOTE or oversampling. The code states: "Proceeding without SMOTE. Using original class distribution."

Why? The 78:22 ratio is moderate (not extreme like 99:1). Oversampling can introduce synthetic noise, and ROC-AUC already handles imbalance well. The model learns from real patterns rather than artificial ones.

Decision 4: Modular Pipeline Architecture

We separated the project into Data Ingestion → Data Transformation → Model Training as independent components connected by a pipeline.

Why? This allows us to save the preprocessing object (scaler + encoder) alongside the trained model. At prediction time, new data goes through the same transformation, ensuring consistency between training and inference.

8. Quick ML Concepts You Need to Know

What is Classification?

Classification is predicting a category (not a number). Examples: Is this email spam or not? Will this patient have cancer? Will this customer default? The model learns from labeled examples and categorizes new unseen data.

What is Training vs Testing?

Training data is what the model learns from (like studying textbook problems with answers). Test data is kept hidden and used only to evaluate (like the final exam). If a model memorizes training data but fails on test data, it has "overfitted" — like a student who memorized answers but doesn't understand concepts.

What is ROC-AUC?

ROC Curve Explained Simply

AUC = 0.5 means random guessing. AUC = 1.0 means perfect. Our model achieves 0.814, which is good for a real-world financial dataset.

What is Overfitting?

Overfitting happens when a model memorizes the training data instead of learning general patterns. It performs great on training data but poorly on new data. Imagine a student who memorized every answer in the textbook but can't solve slightly different questions on the exam.

How we prevent it: Train-test split (only train on 80%), cross-validation (GridSearchCV), and limiting model complexity.
