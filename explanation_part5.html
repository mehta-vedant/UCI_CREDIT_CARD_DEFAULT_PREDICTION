1 Model Evaluation Metrics Explained

Training a model is only half the battle. Knowing how to measure it is what separates good ML engineers from great ones. Here we explain every metric we used, why we chose ROC-AUC as primary, and what the numbers actually mean.

ROC-AUC Score (Primary Metric) — 0.814

The Receiver Operating Characteristic - Area Under Curve is our primary metric. It measures the model's ability to distinguish between defaulters and non-defaulters across all possible classification thresholds.

Analogy: Think of ROC-AUC as a test score. 50% is pure guessing (a coin flip). 100% is a perfect oracle. Our 0.814 means the model has an 81.4% chance of correctly ranking a random defaulter higher than a random non-defaulter. In the medical world, an AUC of 0.8+ is considered "good" for a diagnostic test.
What does 0.814 mean practically?
If we pick one customer who defaulted and one who didn't, our model correctly ranks the defaulter higher 81.4% of the time. The remaining 18.6% is where the model gets confused — but it's far better than a random guess (50%).

Accuracy — 82.3%

Accuracy is the most intuitive metric: what percentage of all predictions were correct? However, it's dangerously misleading with imbalanced data.

Why accuracy lies with imbalanced data:
Our dataset has ~78% non-defaulters and ~22% defaulters. If a "model" simply predicts "No Default" for every customer, it achieves 78% accuracy — while catching zero defaulters! Our 82.3% accuracy is only 4.3% better than this useless baseline, yet the model is actually much more useful than that number suggests.
Example: Imagine a fire alarm that never goes off. It's "correct" every day there's no fire (99.9% of days). But the one day there IS a fire, it fails completely. Its accuracy is 99.9%, yet it's useless. That's why we need better metrics.

Precision — "The False Alarm Rate"

Precision = TP / (TP + FP) — Of all the customers we flagged as "Will Default", how many actually did default?

# From our classification report (model_trainer.py:107) classification_report(y_test, predicted, output_dict=True) # Example output: # Class 0 (No Default): precision=0.84 recall=0.95 f1=0.89 # Class 1 (Default): precision=0.68 recall=0.38 f1=0.49
Analogy — Airport Security: Precision is like the security scanner. High precision means few false alarms (innocent passengers pulled aside unnecessarily). Low precision means tons of false alarms — everyone gets stopped, wasting resources. In credit, low precision means rejecting good customers.

Recall (Sensitivity) — "The Catch Rate"

Recall = TP / (TP + FN) — Of all the customers who actually defaulted, how many did our model catch?

Analogy — Cancer Screening: Recall is like a cancer screening. Missing a cancer patient (false negative) is far worse than a false alarm (false positive). You want HIGH recall even if precision drops. In credit risk, high recall means we catch most defaulters — protecting the bank from losses, even if we occasionally flag good customers.
The Precision-Recall Tradeoff:
We can't maximize both simultaneously. Catching more defaulters (higher recall) usually means more false alarms (lower precision). The ROC-AUC metric elegantly captures this tradeoff across all thresholds, which is why we use it as our primary metric.

F1-Score — "The Balance"

F1 = 2 × (Precision × Recall) / (Precision + Recall) — The harmonic mean of precision and recall. It balances both concerns into a single number.

When to use F1: F1 is most useful when you care about both false positives and false negatives equally. It penalizes extreme imbalances. If precision=0.95 but recall=0.20, the F1 is only 0.34 — correctly reflecting the model's weakness despite the high precision.

Confusion Matrix

The confusion matrix gives a complete picture of all four possible outcomes. It's the foundation for computing precision, recall, and F1.

Cost Asymmetry: In credit default prediction, a False Negative (missing a defaulter) is far more costly than a False Positive (flagging a good customer). The bank loses the full unpaid bill in an FN, but only loses potential interest in an FP.

3 Why XGBoost Won

XGBoost edged out competitors for several specific reasons tied to this dataset's characteristics:

1. Sequential Error Correction

XGBoost builds trees sequentially. Each new tree focuses on the errors (residuals) of the previous ones. For credit data, this means the model can first learn obvious patterns (payment delay = high risk), then fine-tune on subtler signals (utilization trends).

2. Regularization Built-In

XGBoost has L1 and L2 regularization to prevent overfitting. With 30,000 rows and 41 features (24 original + 17 engineered), overfitting is a real risk. XGBoost's regularization helps it generalize better than CatBoost's default settings.

3. Handles Missing Values

Our data has some missing bill amounts and payment statuses. XGBoost has a native algorithm for handling missing values during tree splits, learning the best direction (left or right) for missing data at each node.

4. Efficient with Tabular Data

Gradient boosting methods consistently win Kaggle tabular competitions because they naturally model feature interactions. The combination of PAY_0 + BILL_AMT1 + LIMIT_BAL creates a powerful signal that linear models can't capture.

4 Model Artifacts

After training, we save two critical files to the artifacts/ directory. These are the "brain" and the "translator" of our prediction system:

artifacts/model.pkl

The trained XGBoost model — all the learned decision trees and their splits. This is what makes predictions. Without this, the trained knowledge is lost.

# model_trainer.py:97-100 save_object( file_path=self.model_trainer_config .trained_model_file_path, obj=best_model )

artifacts/preprocessor.pkl

The preprocessing pipeline (feature engineering + StandardScaler). It ensures new data gets the exact same transformations as training data. Inconsistency = garbage predictions.

# The preprocessor handles: # 1. Feature engineering (17 new features) # 2. StandardScaler for numerical features # Same transforms as training!
Pickle Serialization: Python's pickle module converts a Python object (model, pipeline) into a byte stream that can be saved to disk and loaded later. We need both files because the model only works on scaled, engineered features. Raw user input must go through the preprocessor first.
# utils.py - save_object and load_object import pickle def save_object(file_path, obj): with open(file_path, "wb") as file_obj: pickle.dump(obj, file_obj) def load_object(file_path): with open(file_path, "rb") as file_obj: return pickle.load(file_obj)

6 Web Application Architecture

Our Flask app has three main components working together:

GET vs POST — Simply Explained

GET Request (Loading the form)

When you visit /predictdata, the browser sends a GET request. Flask responds by rendering the blank form (home.html) so you can enter data. No processing happens yet.

if request.method == 'GET': return render_template('home.html')

POST Request (Making a prediction)

When you click "Predict", the form sends a POST request with all 24 field values. Flask extracts them, runs the pipeline, and returns the result rendered back into the same form.

9 Project Strengths

What Was Done Well

  • ✓ Modular Code Architecture — Separate components for data ingestion, transformation, and training. Each piece is testable and replaceable independently.
  • ✓ No Data Leakage — Train/test split happens before any preprocessing. The preprocessor is fit ONLY on training data, preventing information from the test set leaking in.
  • ✓ Multiple Model Comparison — We didn't just pick one algorithm. We tested 6 models with GridSearchCV and let the data decide the winner.
  • ✓ Automated Hyperparameter Tuning — GridSearchCV systematically explores parameter combinations instead of manual guessing.
  • ✓ Production-Ready Deployment — The app runs on Render with proper WSGI server (gunicorn), environment variable handling, and debug mode toggling.
  • ✓ Custom Exception Handling — Custom exceptions and logging throughout the pipeline make debugging production issues straightforward.

11 Lessons Learned

💡 Data Quality > Model Complexity

The 17 engineered features improved performance by ~15%. Feature engineering — understanding the domain and creating meaningful features — had a bigger impact than switching algorithms.

💡 Choose the Right Metric First

Accuracy would have told us our model is "82% good." But with imbalanced data, ROC-AUC revealed the true picture: 0.814 — good but not great. The metric choice changes the entire story.

💡 Separation is Non-Negotiable

Train/test split BEFORE any preprocessing. Fitting the scaler on the entire dataset would leak future information and give falsely optimistic scores. This is the #1 beginner mistake.

💡 Simpler Models Have Their Place

Logistic Regression was only ~5% worse. In production, you might prefer it for its speed, interpretability, and ease of deployment. Always consider the tradeoffs.

💡 Deployment is a Skill Too

Getting a model from a Jupyter notebook to a live web app involves Flask, WSGI servers, environment variables, and cloud platforms. It's a completely different skill set from ML.

💡 Modular Code Saves Time

The component-based architecture (DataIngestion → DataTransformation → ModelTrainer) meant we could change one part without breaking others. This is essential for real ML projects.

The Big Picture:

Machine learning isn't just about algorithms. It's a full engineering discipline that spans data collection, cleaning, feature engineering, model training, evaluation, deployment, and monitoring. This project demonstrates that entire pipeline — from a CSV file to a live web application that anyone in the world can use. The technical skills you've learned here transfer directly to professional ML engineering roles.
