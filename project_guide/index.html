What does this application do?

A credit card company has old records of customers: their credit limit, recent bill amounts, recent payments, and whether they later failed to make the next month's payment. This project learns patterns from those old examples. Given a new record with the same kind of information, it returns an estimated probability of next-month payment default.

Default is not fraud. Fraud detection asks, “Is this transaction suspicious?” This project asks, “Based on this client's recent credit history, how likely is a missed next payment?” The two problems use different data and have different consequences.

Why choose this project?

It is a strong learning project because it is a real tabular classification problem with a meaningful mistake trade-off. A missed defaulter may cause financial loss. Flagging someone who would have paid on time can create unnecessary review and unfair treatment. That trade-off forces you to go beyond “the model has good accuracy.”

It also gives you an end-to-end engineering story: clean data, reproducible training, several models, evaluation, one saved model artifact, a Flask website, a JSON API, tests, Docker, CI, and deployment. In an interview, that is much more convincing than saying you trained one notebook model.

The responsible framing: this is an educational risk-review prototype built from an academic 2005 Taiwan dataset. It must never be presented as a system that automatically approves or denies real people.

The dataset in ordinary language

The source is UCI's Default of Credit Card Clients dataset. Every row represents one client. The target column, default.payment.next.month, is the historical answer: 1 means that client defaulted next month; 0 means they did not.

The raw file has 30,000 rows and 25 columns. The model uses 23 fields because ID is only an identifier and the target is the answer to learn, not an input. The default class is the minority class: 6,636 defaults and 23,364 non-defaults.

What happens from CSV file to prediction?

Think of the model as a student. Training data is the student's textbook with answers. Test data is the exam the student has never seen. We need the separation because scoring the student on the textbook tells us very little about how they will do on new examples.

Step 1: validate and clean fields

validate_features() checks that all 23 fields exist, converts values to numbers, rejects impossible credit limits and ages, and refuses negative category codes. This prevents a malformed web request from quietly becoming a meaningless prediction.

Step 2: create useful derived features

The project calculates credit utilisation, payment-to-bill ratios, average and maximum payment delay, the number of delayed months, payment and bill averages, and trends. For example, latest bill divided by credit limit expresses the same debt in a more useful context. A 50,000 bill is 50% utilisation at a 100,000 limit.

Step 3: prepare values for models

Numeric values are median-imputed and standardized. Categorical codes are most-frequent-imputed and one-hot encoded. All of this is inside the saved scikit-learn pipeline. The important reason is consistency: the model sees exactly the same transformations during training and on the website.

Data leakage: leakage happens when information from validation or test rows helps fit a transformation or model. It produces flattering numbers that disappear in real use. The pipeline is fitted only on training folds inside model search.

How the model was chosen

Three different classifiers compete. Logistic Regression is a simple baseline that combines inputs with learned weights. Random Forest averages many decision trees. CatBoost is a boosted-tree method: it builds trees in sequence, where later trees focus on mistakes earlier trees made. Tree models can learn interactions, such as repeated payment delays combined with high utilisation.

The code uses shuffled StratifiedKFold cross-validation. “Stratified” means every fold keeps roughly the same default rate. The standard run uses three folds. Each candidate has a small parameter grid, and the search chooses its best settings using ROC-AUC on training folds only.

The selected CatBoost settings are depth=6, iterations=150, learning_rate=0.03, and l2_leaf_reg=3. Depth limits each tree's complexity; iterations is the number of trees; learning rate controls how strongly each tree changes the result; L2 regularization helps discourage overfitting.

Metrics: what the numbers mean

A prediction becomes a class only after choosing a threshold. The application uses 0.245, selected on validation data to maximize F1. A probability at or above 24.5% creates a review flag; it is not an automatic lending decision.

Which metric is “the most important”? There is no universal winner. ROC-AUC is the training selection metric because it compares ranking ability. Precision, recall, and F1 describe the chosen review threshold. A real bank would set the threshold using documented costs, capacity, fairness, and regulation rather than copying this educational F1 policy.

The central prediction idea

# The saved pipeline includes the feature engineer and the CatBoost classifier.
features = validate_features(pd.DataFrame([payload]))
probability = float(pipeline.predict_proba(features)[0, 1])
prediction = int(probability >= metadata["threshold"])

predict_proba(...)[0, 1] means “for the first submitted row, give me the probability of class 1,” where class 1 is recorded default. The code then compares it to the saved threshold. Keeping the threshold in model metadata means the website does not silently use a different rule from the evaluation run.

How to put the real app online

Recommendation: deploy the Flask application on Render as a Docker web service. The repository contains a Dockerfile that runs Gunicorn and honors the hosting platform's PORT value. It includes the already-evaluated model artifact instead of silently retraining during deployment. Create the Web Service directly in the Render dashboard and use the /health endpoint as its health check.

HostFit for this appRecommendation
RenderRuns a normal Docker/Flask web service, supports health checks, environment ports, and Git-based deploys.Use this first. It matches the current Docker deployment design.
Hugging Face SpacesCan run custom Docker containers and makes a good ML portfolio demo.Use as an optional public demo later. It needs a Space-specific README configuration and port 7860.
VercelCan deploy Flask through Python serverless functions, but the app is loaded as a serverless function.Keep it for a static portfolio or documentation. It is not the first choice for this model-loaded Flask application.

Render deployment steps

  1. Push the current main branch to GitHub. The repository is already configured for this.
  2. Create a Render account and connect GitHub.
  3. Click New → Web Service, then select this repository.
  4. Set Language to Docker. Leave Dockerfile Path at ./Dockerfile and Docker Context at the repository root. Render will use the Dockerfile's command.
  5. Select the free instance, give the service a name, and set the health-check path to /health.
  6. Deploy. Render supplies PORT; the Docker command binds Gunicorn to it.
  7. When the deploy completes, open https://your-service.onrender.com/health. It should return {"status":"ok", ...}. Then open the root URL for the form.
  8. In the service settings, enable automatic deployment from main. If your account exposes “After CI checks pass,” select it; otherwise use deploy-on-commit and check GitHub Actions before relying on a new release.
Free-tier expectation: free web services can sleep after inactivity. The first request after a sleep may be slow. That is acceptable for a portfolio demo; use a paid service and proper monitoring if you need reliable availability.

What “reproducible online” means here

Every visitor receives predictions from the same committed credit_risk_pipeline.joblib, with the same saved threshold and pinned package versions. Anyone can reproduce the training workflow locally using the included raw UCI file and seed 42. It does not mean their result must be identical across every operating system and future hardware/library release; that is why the deployed artifact and pinned dependencies are important.

A natural interview explanation

“I built a credit-risk prediction prototype using the UCI Default of Credit Card Clients dataset. The problem is to estimate the chance that a client will default next month from their credit limit, recent payment status, bill amounts, and payment amounts. I treated it as a binary classification problem, not fraud detection.

I built a scikit-learn pipeline that validates the 23 inputs, creates repayment and utilisation features, imputes and scales numeric values, and encodes categories. I split the data into stratified training, validation, and final test sets. I compared Logistic Regression, Random Forest, and CatBoost with three-fold cross-validation, using ROC-AUC to choose the best ranking model. CatBoost won.

I selected the operational threshold on validation data using F1 rather than assuming 0.5. On the untouched 6,000-row test set, the model reached 0.7805 ROC-AUC, 0.5998 recall, and 0.4941 precision at the 0.245 review threshold. I packaged the full pipeline into one joblib artifact and served it through Flask, a browser form, and a JSON API. I also added tests, Docker, CI, health checks, and SHAP global explanations. I would not use it for automatic lending because the data is historical and limited, and production would need fairness, calibration, governance, and monitoring.”

Why did you use ROC-AUC to select the model?

It measures ranking quality over every possible threshold. At model-selection time, I want to know which candidate separates likely defaults from non-defaults most reliably before deciding how many cases an operations team can review.

Why is accuracy not enough?

Because 77.88% of rows are non-default. A useless model that always predicts no default would already look 77.88% accurate while catching none of the defaults. Recall, precision, PR metrics, balanced accuracy, and the confusion matrix expose that failure.

Why is the threshold 0.245 instead of 0.5?

The threshold is a business policy layer. In this prototype it is the point that maximized validation F1. A real institution would choose it from the cost of a missed default, the cost of reviewing a customer, operational capacity, fairness analysis, and regulation.

What remains outside the scope

  • No model can establish that a person will default. It produces a statistical estimate from historical patterns.
  • The dataset describes one historical population. It does not prove that the model works today, in another country, or for a bank's customer base.
  • SHAP describes how the model used inputs in a sample. It does not prove causation or solve adverse-action explanation requirements.
  • Production use needs authentication, rate limiting, secure logging, fairness and bias testing, calibration monitoring, drift detection, a retraining approval process, privacy review, human review, and an appeal process.
