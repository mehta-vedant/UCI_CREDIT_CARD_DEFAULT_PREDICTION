What this means

data_ingestion.py loads/splits. data_transformation.py defines the custom feature engineer and sklearn ColumnTransformer. model_trainer.py sets candidates/grids and saves winner. utils.py serialises and evaluates. train_pipeline.py orchestrates. predict_pipeline.py maps web/API inputs to DataFrame and predicts. application.py is Flask routes; api/predict.py handles JSON; app/ is Next.js UI.

A DataFrame is a labelled table; a NumPy array is a numerical matrix. A function is reusable named behaviour; a class groups data/behaviour; CustomData(...) instantiates an object; a method belongs to an object. Dataclasses here hold config. Random state supports reproducibility. SHAP/matplotlib imports and an image exist, but active trainer does not generate SHAP output.

Read code by following the data

Begin at train_pipeline.py. It creates a DataIngestion object, then calls its method. That method uses pandas read_csv to make a DataFrame, then sklearn's train_test_split to create two DataFrames and write them to artifact CSV files. The transformation component reads those two files again, separates the target column from the feature columns, and turns feature tables into numerical arrays. The trainer receives arrays where the final column is the target.

This style can look intimidating because it uses classes, dataclasses and imports. You can translate it into simple questions: what value goes into this function? What does it return? Does it change the data, fit something, save something, or call another component? For example, CustomData.get_data_as_data_frame() returns a one-row table with exact column names. It does not predict anything. The prediction method takes that table and performs the saved transformations.

Files that are easy to confuse

src/pipeline/tempCodeRunnerFile.py looks like an editor scratch file and is not the active inference import. The project also has several copied or experimental folders. Some contain incompatible fraud wording or unrelated older code. The active root imports and artifact paths are the reliable guide: src/, artifacts/, application.py, api/predict.py, and the root raw CSV path.

Persistence

Pickle serialisation writes a Python object to a file and reads it back later. It is convenient for a local trusted project. Never load unknown pickle files from the internet because pickle loading can execute malicious code. In a mature deployment, you also record package versions, artifact checksums, model version, data version and compatibility tests.

Check understanding

Try each aloud before opening it: five beginner, five intermediate and two challenging questions.

Beginner — What is the target?

default.payment.next.month: 1 means default, 0 no default.

Beginner — Is this transaction fraud?

No. Root project is next-month client default prediction.

Beginner — What is a feature?

An input clue such as PAY_0 or LIMIT_BAL.

Beginner — Why test data?

To estimate performance on records not used to fit.

Beginner — What limitation matters?

It is historical Taiwan 2005 data, not production lending data.

Intermediate — Evidence for claim?

Cite active root source, paired artifacts, data inspection or recomputed metrics.

Intermediate — What ranks thresholds?

ROC-AUC; active GridSearchCV uses it.

Intermediate — Why can accuracy mislead?

Always predicting no default yields 77.88% accuracy and zero recalls.

Intermediate — What is leakage?

Evaluation/future information influences fitting.

Intermediate — What must accompany model.pkl?

preprocessor.pkl because it produces the expected 42 features.

Challenge — Best improvement?

Select on train-only stratified CV, reserve test, then choose threshold/calibration by cost.

Challenge — Interview summary?

Educational default-risk prototype with evidence-based limits, not a production decision system.
