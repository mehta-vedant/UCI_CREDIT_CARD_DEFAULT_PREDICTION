Prototype to responsible system

There are local serving interfaces, not a safe automated lending system.

What this means

Implemented: pickle persistence; paired preprocessing; Flask form; JSON handler; Next.js form. Missing: schema/range/domain validation, authentication, rate limiting, safe errors, restricted CORS, audit logs, drift/retraining, calibration, monitoring, fairness testing and governance. The API returns tracebacks and uses CORS *—fine for prototype diagnosis, not production.

What changes when people rely on a prediction

A notebook or local form can assume friendly inputs and a developer watching the screen. A real service cannot. It needs to reject impossible ages, unknown category codes, missing fields, huge payloads and unauthorised requests. It needs safe error messages that help the user without exposing internal stack traces. It also needs to keep personal financial information out of logs unless there is a lawful, protected reason to retain it.

Deployment is not the same as copying a pickle file to a server. The model, preprocessor and input schema must travel together as a versioned unit. Every prediction should be traceable to a model version and policy version. Monitoring has to check whether new client inputs have changed, whether actual outcomes still match predictions, and whether scores remain calibrated. Once real outcomes arrive, the team needs a controlled retraining process rather than silently replacing a model.

Human and legal safeguards

Credit decisions can affect housing, work, health and financial security. Demographic fields and historical patterns can reproduce unfair treatment even when a model has a good aggregate metric. A production setting needs legal review, fairness testing, explainability appropriate to the decision, human oversight, adverse-action procedures where required, consent/privacy controls and an appeal route. The current repository does not implement these controls.

A realistic next milestone

Before any external use, build a small internal-only service with strict schema validation, authentication, safe logging, a versioned pipeline, test coverage, a monitored dashboard and a human-review-only workflow. Then evaluate the data, policy and fairness questions with the people responsible for risk, law, privacy and operations.

Check understanding

Try each aloud before opening it: five beginner, five intermediate and two challenging questions.

Beginner — What is the target?

default.payment.next.month: 1 means default, 0 no default.

Beginner — Is this transaction fraud?

No. Root project is next-month client default prediction.

Beginner — What is a feature?

An input clue such as PAY_0 or LIMIT_BAL.

Beginner — Why test data?

To estimate performance on records not used to fit.

Beginner — What limitation matters?

It is historical Taiwan 2005 data, not production lending data.

Intermediate — Evidence for claim?

Cite active root source, paired artifacts, data inspection or recomputed metrics.

Intermediate — What ranks thresholds?

ROC-AUC; active GridSearchCV uses it.

Intermediate — Why can accuracy mislead?

Always predicting no default yields 77.88% accuracy and zero recalls.

Intermediate — What is leakage?

Evaluation/future information influences fitting.

Intermediate — What must accompany model.pkl?

preprocessor.pkl because it produces the expected 42 features.

Challenge — Best improvement?

Select on train-only stratified CV, reserve test, then choose threshold/calibration by cost.

Challenge — Interview summary?

Educational default-risk prototype with evidence-based limits, not a production decision system.
