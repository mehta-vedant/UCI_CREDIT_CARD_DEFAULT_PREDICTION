From raw credit history to a review-ready probability

This is an end-to-end machine-learning project for estimating next-month credit-card payment default. It uses UCI's historical Taiwan credit-card dataset, not transaction-fraud data, and it is presented as an educational risk-review prototype rather than an automated credit decision system.

The problem

Why this project matters

A lender needs to decide where to focus review effort. Missing a likely default can create financial loss; flagging someone who would pay on time creates unnecessary review and can be unfair. The model provides one probability signal from historical patterns. It does not make a final decision about a person.

Input

Credit limit, recent repayment status, bill amounts, and payment amounts across six months.

Output

A probability of class 1: recorded next-month payment default.

Human use

A review flag only. Real lending requires policy, fairness checks, human oversight, and an appeal process.

EDA

Data quality and exploratory analysis

EDA happens before model fitting. It checks whether the data is complete, whether one class dominates, what the distributions look like, and which patterns are worth investigating. The public page shows aggregate findings only, never individual customer rows.

Feature engineering

Turning 23 raw fields into model-ready evidence

The active pipeline creates all features at training and prediction time. That is important: the website cannot accidentally calculate inputs differently from the model experiment.

Utilisation

BILL_AMT1 / LIMIT_BAL puts the newest bill in the context of available credit.

Payment behaviour

Payment-to-bill ratios, average status, maximum delay, delayed-month count, and early-payment flag summarize the six-month history.

Trend signals

Average bill/payment amounts plus bill/payment slopes describe whether balances and payments are rising or falling.

What preprocessing happens after feature engineering?

Numeric fields receive median imputation and StandardScaler. Categorical fields receive most-frequent imputation and one-hot encoding. The fitted feature transformer and CatBoost model are stored together in one joblib pipeline.

How is leakage avoided?

The data is split with stratification into 60% training, 20% validation, and 20% final test data. Model selection happens through shuffled stratified cross-validation on the training partition. The validation partition selects the operating threshold. The final test set is evaluated after those choices.

Model selection

Three models were compared

The active project compares Logistic Regression, Random Forest, and CatBoost using the same preprocessing pipeline and three-fold stratified cross-validation. ROC-AUC selects the best ranking model.

Explainability

What tends to influence the model?

Global explanation, careful wording

Recent repayment status, maximum delay, delay count, credit utilisation, and payment amounts are useful to the trained model. This does not mean any one variable determines a person's future. The model learns statistical patterns from historical data.

Important limitation: SHAP is not a substitute for fairness analysis, legal review, adverse-action notices, or a human appeal process.

Honest limits

What this project does not claim

This is not a credit-approval engine. The data is historical, from one population and period, and includes demographic fields. A strong offline metric does not establish fairness, legal compliance, calibration in a live population, or suitability for an automated decision.

Data limit

No present-day or external validation. A real organization needs representative current data and monitored outcomes.

Model limit

Offline performance can drift. The project has no live drift monitoring or approved retraining process.

Decision limit

Production use needs security, privacy, fairness testing, documented policy, human review, and an appeal path.
