2-minute version

Walk the interviewer through it

  1. Problem: “A lender wants an early warning signal so staff can prioritise human review or support. It is not an automatic approval or denial system.”
  2. Data: “The dataset contains 30,000 historical Taiwan client records, with credit limits, six months of repayment statuses, bills, payments, and a next-month default label. Defaults are 22.12%, so accuracy alone is misleading.”
  3. EDA: “I checked missing values, duplicates, distributions, target imbalance, repayment-status rates, correlations, and a heatmap. Recent repayment behaviour had the strongest raw association with default, but I treated that as association, not causation.”
  4. Features: “I added credit utilisation, payment-to-bill ratios, delay summaries, average bills/payments, trends, and flags. Every engineered value uses only information available before the target month.”
  5. Training: “I split data into train, validation, and untouched test partitions. The broad benchmark uses five-fold cross-validation for model selection and keeps resampling inside training folds.”
  6. Results: “I choose the operating threshold on validation data, then report the final test metrics once. The key metrics are average precision, ROC-AUC, precision, recall, F1, log loss, calibration, and the confusion matrix.”
  7. Deployment: “The saved artifact contains preprocessing and the model together, so the Flask website cannot accidentally transform inputs differently from training.”
  8. Limits: “This is an academic historical dataset. Real credit use would require current data, fairness analysis, security, monitoring, documented policy, human review, and an appeal process.”
Interviewer interruptions

Questions you should expect

Why did you choose this project?

What they are testing: Whether you understand the business problem.

Answer: “It is a realistic tabular classification problem with a real error trade-off. Missing a likely default can increase loss, but flagging someone who would pay can create unnecessary review and unfair treatment. That forces me to work beyond accuracy and build a full pipeline.”

Is this fraud detection?

Answer: “No. Fraud detection asks whether a transaction is unauthorised and usually needs transaction-level signals like merchant, device, location, and time. This project predicts next-month payment default from client credit history.”

What features did you add, and why?

Answer: “I created utilisation to compare a recent bill with available credit; payment ratios to compare payments with amounts owed; average and maximum repayment status to summarise a six-month history; delay counts and early-payment flags for behavioural signals; and bill/payment trends to capture direction over time. I kept them past-only to avoid leakage.”

What is encoding and why did you use it?

Answer: “Education and marriage are dataset categories, not measured quantities. One-hot encoding turns a category into yes/no columns so the model does not assume code 2 is mathematically twice code 1. Numeric columns are imputed and standardised inside the training pipeline.”

Why not use accuracy as your main metric?

Answer: “Only 22.12% of records are defaults. A model that always predicts no default gets about 77.88% accuracy and catches none. I use average precision and ROC-AUC to assess ranking, then precision, recall, F1, and confusion matrices for the selected threshold.”

What is ROC-AUC?

Answer: “ROC-AUC measures whether the model generally ranks a randomly selected default above a randomly selected non-default across many thresholds. It is useful for comparing ranking models, but precision-recall metrics are especially important here because defaults are the minority class.”

Why would you value precision over recall, or recall over precision?

Answer: “It depends on the workflow. Higher recall catches more possible defaults but creates more review work and false positives. Higher precision gives staff fewer, more credible flags but misses more defaults. This prototype uses validation F1 as a balanced technical rule and publishes other thresholds rather than pretending one cutoff fits every bank.”

Why is the threshold not automatically 0.50?

Answer: “0.50 is only a default convention. The model produces a probability; a threshold converts it into an action. I select the threshold on validation data according to F1, never on the final test set.”

How did you avoid data leakage?

Answer: “I split before fitting. Feature engineering, imputation, encoding, scaling, and any sampler live inside pipelines so each cross-validation training fold fits its own transformations. Validation selects the threshold. The test partition stays untouched until final reporting.”

Why test many models instead of only CatBoost?

Answer: “A strong-looking model is not automatically the best choice. The benchmark includes a dummy baseline, linear, distance-based, naïve Bayes, single-tree, ensemble, boosting, CatBoost, and XGBoost families. I select using the same cross-validation protocol, not familiarity.”

What is SMOTENC and why is it safe here?

Answer: “SMOTENC creates synthetic minority examples while respecting categorical fields. It is only fitted inside cross-validation training folds, after past-only feature engineering and before one-hot encoding. Validation and test data are never resampled.”

What is the difference between correlation and feature importance?

Answer: “Correlation is a raw one-variable linear association. Feature importance describes how a fitted model used transformed features with other features present. Neither proves causation.”

What would you improve with another week?

Answer: “I would add temporal validation if timestamps existed, external data validation, fairness/subgroup analysis, calibration comparison, cost-aware threshold policy, authenticated APIs, monitoring, feedback labels, and a governed retraining process.”

Strong closing sentence

“The project is strongest as a reproducible end-to-end machine-learning and engineering demonstration. I can explain the data, feature logic, leakage safeguards, model comparison, threshold trade-off, deployment path, and limits. I would never present the offline score as permission to make an automated credit decision about a real person.”
